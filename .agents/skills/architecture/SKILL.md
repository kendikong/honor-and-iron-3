# Technical Architecture (Godot 4)

## Core Philosophy: The Simulation is the Game
Visuals are merely a representation of the simulation. Visual code must never determine gameplay outcomes.
- All gameplay must be capable of running **headless** (without rendering, animations, UI, or networking).
- **Golden Rule**: Gameplay never asks the renderer for information; the renderer always asks gameplay (e.g. Simulation -> Signal -> Animation, NOT Animation Finished -> Apply Damage).

## Folder Structure
- `res://core/` — Combat, timeline, grid, units, abilities, terrain, enemy, resources
- `res://ui/` — Timeline UI, health bars, inventory, buttons
- `res://scenes/` — Main scene tree, presentation setups
- `res://effects/` — Particle assets, visual effects
- `res://audio/` — Sound effects, music
- `res://save/` — Save file schemas and configurations
- `res://debug/` — Testing tools and developer panels
- `res://tests/` — Automated test files

## Layered Architecture (4 Layers, Depend Downward Only)
1. **UI**: Timeline UI, Health Bars, Buttons, menus.
2. **Presentation**: Sprites, Animations, VFX, Sounds (reacts to signals from Simulation).
3. **Simulation**: Grid coordinates, Combat, Timeline state, Physics collision, Enemy AI (runs headlessly on RefCounted objects).
4. **Data**: Godot Resources containing values, rules, and metadata. Resources must never reference Nodes.

## Scene vs. Resource Responsibilities
- **Scenes & Nodes**: Handle rendering, animations, audio, mouse hover/clicks, selection, and VFX. Never compute damage, movement paths, timeline queues, or AI decisions.
- **Resources**: Contain unit stats, class data, ability definitions, weapons, and status effects. Never reference Nodes.
- **Managers**: Coordinates systems. Own single responsibilities and communicate via signals (e.g. `CombatManager` handles damage, `TimelineManager` handles queue, `GridManager` handles occupancy, `PhysicsManager` handles shoves/collisions).

## Deterministic Simulation & Previews
- **Ghost Previews**: Calculated frame-by-frame on timeline edits.
  1. Duplicate the BoardState and UnitStates.
  2. Replay the timeline headlessly.
  3. Store and pass the resulting state to the renderer to display ghost models.
  4. Discard the duplicated simulation state.
- **Unified Path**: Preview and actual execution use the same code path (`Simulator.simulate(state, timeline)`). Execution commits the state; preview discards it.
- **State Machine**: Combat is in exactly one state: `Planning`, `Executing`, `Enemy Turn`, `Victory`, `Defeat`, or `Paused`.

## Combat Resolution Order (Fixed)
1. Movement
2. Displacement (Shoves, Pulls)
3. Collision
4. Damage
5. Break Gauge
6. Death
7. Status Effects
8. Terrain interactions
9. Reactions (Opportunity attacks, counters)
10. Timeline updates

## Save & Networking
- Everything to reconstruct combat must be serializable (RNG seed, board, units, terrain, timeline, upgrades, encounters).
- **Deterministic Action Sync**: LAN/online co-op must only sync lightweight player input actions (e.g. cursor position, pings, timeline modifications, ready status). Never sync raw board states, node trees, or rendering frames mid-simulation.
- **Synchronized PRNG Seeds**: All non-combat random parameters (rewards, procedural generation, enemy variants) must use a synchronized pseudo-random number generator (PRNG) initialized with a shared seed generated by the host.
- **Local Preview Execution**: The host holds the master simulation state, but both host and clients execute `Simulator.simulate(state, timeline)` locally. This generates matching timeline previews and ghost models.
